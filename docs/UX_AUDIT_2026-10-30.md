# CityHive feature inventory and usability audit — 30 October 2026

Status: **audit only. No application code was changed.** Nothing here is implemented until approved.

## How this was done

- Ran the app locally (FastAPI on :8000, built frontend on :5180, SQLite with the demo data: 2 branches, 112 rooms, 21 residents, 39 invoices, 7 admissions, 4 complaints).
- Signed in as the owner and opened all 13 admin menu items.
- On each page I recorded headings, filters, table columns and buttons. I opened 18 forms/modals (Cancel only, nothing submitted) and recorded every field.
- Read the route list (`backend/app/main.py`, 82 routes) and the model list (`backend/app/models.py`, 29 tables) to map screens to APIs and tables.
- Not covered: the resident portal was only exercised for "My stay / room-change request" and the forced password change; branch-admin screens were not walked separately (same pages, filtered by branch); WhatsApp/SMS/email delivery cannot be exercised locally.

## 1. What the data model actually knows

| Concept | Stored as | Consequence |
|---|---|---|
| Room | `rooms`: number, floor, **capacity**, **monthly_fee**, active, ac, branch | Capacity and fee are typed in per room |
| Bed | **No table.** A bed is only "capacity minus residents in the room" | "Which bed is vacant?" cannot be answered. Only counts can |
| Who is in a room | `residents.room_id` (+ `allocation_events` history) | Occupancy is already derived from residents, good. It is not re-entered |
| Price | **Two sources:** `rooms.monthly_fee` and `fee_plans.monthly_fee` (per branch + sharing + date). An invoice uses the plan if one is assigned, otherwise the room fee | Admins must keep two price lists in sync. Today every room fee is ₹0 while plans carry the real prices |
| Advance/deposit | `fee_plans.advance_amount` (configured) and `financial_ledger_events` (actually received) | Configured advance is never pre-filled into the "received" form |
| Resident onboarding | `admissions` → `users` + `residents` → `residents.room_id` → `residents.fee_plan_id` → ledger → ID review | Five separate screens/steps |

## 2. Feature inventory (admin panel)

For each: purpose · who · what the user types · what the system could fill or calculate · problems · simplification.

### Overview
- **Purpose:** daily snapshot. **Who:** owner, branch admin.
- **Contains:** 4 metric cards, 6 operations cards, Branch overview (6 metrics + 3 tables), "A home for everyone" room preview, follow-up buttons, Recent residents table. The page renders about 70 table rows.
- **Typed:** nothing (read-only). **APIs/tables:** `/dashboard`, `/rooms`, `/invoices`, `/residents`.
- **Problems:** too long. The pending-fee list (up to 50 rows) and beds-to-fill list (40 rows) bury the cards. Cards are not clickable (no jump to "overdue invoices", "pending admissions"). "Recent residents" repeats the Residents page with all its action buttons. The room preview shows 4 arbitrary rooms.
- **Simplify:** top row of clickable KPI cards; one branch selector at the top of the page driving everything; move the two long tables to their own pages (Rooms, Fees) and show only top 5 here.

### Branches
- **Purpose:** branch master data and public publishing. **Who:** owner (branch admins view).
- **Typed:** name, address, phone, email, photo URL, status, description, facilities, house rules, notice days. FAQs edited in a second dialog. Publish is a separate button with hidden preconditions (address + description + at least one room).
- **Problems:** the Edit dialog is titled **"Add a branch"** (wrong title). Two photo mechanisms (one URL per branch). Facilities is a comma-separated textarea. Publish failure reasons only appear as a checklist on the card. No bed or occupancy totals on the card.
- **Simplify:** fix title; show occupancy and beds on the card; tick-list facilities; one "Publish" with inline reasons.

### Branch admins (owner only)
- **Typed:** email, WhatsApp mobile, temporary password (12+), authorized branches (multi-select needing Ctrl/Cmd).
- **Problems:** the multi-select with a "hold Ctrl/Command" instruction is easy to get wrong. The WhatsApp mobile is required even though sign-in no longer sends codes. Temporary password typed by the owner and shared manually.
- **Simplify:** checkboxes per branch; make the mobile optional; generate the temporary password and show it once.

### Admissions
- **Purpose:** public enquiries into residents. **Typed by admin:** a decision and a message; then "Create resident" asks only for a temporary password.
- **Good:** filters (search, branch, status, move-in range), history view, applicant data carried forward.
- **Problems:** after "Create resident" the admin must still find the new resident, allocate a room, assign a fee plan, record deposit/advance, review ID. Nothing links these. The temporary password is invented by staff each time.
- **Simplify:** one "Onboard" wizard from an approved admission: choose room (pre-filtered to the applicant's branch and sharing preference and showing only vacancies), fee plan auto-selected from branch + room sharing, advance pre-filled from the plan, password generated. Same existing steps, done in one flow.

### Stay requests
- **Purpose:** extension / shift / vacating decisions. Table shows resident, type, requested date or room, status, action. Button "Process due move-outs" is a global operation with no preview.
- **Problems:** empty on demo data (not exercised end to end). "Process due move-outs" runs without showing what it will do.
- **Simplify:** preview the residents it will move out before confirming.

### Residents
- **Purpose:** resident register. **Typed to add:** branch, name, email, phone, joining date, guardian name and phone, college/workplace, Aadhaar last 4, temporary password. Room, fee plan and fee are not asked here.
- **Row actions:** Review (ID), Edit/Allocate room, Financial account, Fee plan, Deactivate. Six controls per row.
- **Problems:** the filter labelled "Room" really means allocated/unallocated. Resident created without a room shows "—" fee. Adding a resident directly bypasses admissions, so there are two ways in. "Fee plan" is a separate action even though the plan is fully determined by branch + room sharing + date. The ID "Review" modal asks the admin to re-type the Aadhaar last 4 that they already entered when adding the resident.
- **Simplify:** keep the row action set, but group under one "Manage" menu; assign the fee plan automatically when a room is allocated (keep manual override); pre-fill Aadhaar digits in review; rename the filter "Room status".

### Rooms
- **Purpose:** inventory. **Typed to add:** branch, room number, floor, sharing capacity, AC/Non-AC, fee per resident per month.
- **System already derives:** occupied count, vacant count, occupants (shown in Edit room and on tiles since this week), branch grouping, AC flag.
- **Problems:** the **fee per resident** typed here competes with fee plans (see section 1). The room tile shows ₹0.00 per resident per month, which is wrong relative to the real plan price. "Floor" is free text ("Floor 1" vs "First" vs "Ground"). Capacity is typed per room though it follows the room type. No bed identity. Number must be unique across all branches, which forced prefixes like `M-101-AC`.
- **Simplify:** show the plan price (read-only) and drop the per-room fee from the form once plans exist; floor as a number; unique per branch, not global; later (only if approved) optional bed labels.

### Fees & payments
- **Contains:** Generate invoices (month), fee plans table + Add fee plan, fee ledger (filters + 69 rows), payment history (PDF, receipt, reverse).
- **Typed (fee plan):** advance, branch, name, sharing, monthly fee, extra-charge label and amount, billing day, due day, effective-from. Ten fields, three of which rarely change (billing day 1, due day 5, extra charge).
- **Typed (record payment):** amount, method, date/time, payer name, reference, note. Amount should default to the invoice balance. The payer defaults to the resident.
- **Problems:** three tables on one page. Plan name has to be typed ("2 Sharing AC") though branch + sharing + AC are already fields. There is no AC on plans, so two plans cannot differ by AC. "Reverse" sits next to "Receipt" in the same row.
- **Simplify:** default plan name from its fields; defaults for billing/due day; default payment amount = balance; split into tabs (Plans / Invoices / Payments); move Reverse behind a confirm.

### Financial analytics
- **Contains:** 10 filters, 8 report tables (157 rows on demo data), CSV export, "Open fee ledger" links.
- **Problems:** the heaviest page, no summary at the top, wide tables. Many filters for occasional use.
- **Simplify:** summary cards first (billed, collected, outstanding, overdue), then tabs for aging / residents / rooms / collections.

### Complaints
- **Purpose:** residents raise, staff assign and respond. **Admin types:** status + response + resolution note; assign staff from a list.
- **Good:** filters (search, branch, status, category, dates).
- **Problems:** complaints appear as large cards, not a table, so triage of many items is slow. Priority and due-by are not captured. Assign and Respond are two separate dialogs.
- **Simplify:** table with inline status; combine assign + respond in one dialog.

### Gate passes
- **Typed:** active resident (22-item dropdown) and optional expiry. Print and revoke from the list.
- **Problems:** a resident dropdown with no search. Empty list until staff issue passes manually.
- **Simplify:** searchable resident field; default expiry (for example end of stay or 30 days).

### Message activity
- **Contains:** the new owner mail sender, "Send reminders & queued emails now", and the delivery log with filters.
- **Problems:** 33 messages in a log with no body preview. Queued messages from local testing stay "retrying" until SMTP is configured.
- **Simplify:** show the message body on click; show a clear "email is not configured" banner when SMTP host is local.

### Account
- **Contains:** service/deployment status and change password. Fine; the service configuration block is long and technical for a typical owner.

## 3. Biggest usability problems (ranked)

1. **Two price sources.** Room fee and fee plan both exist; the UI shows the room's (₹0.00) in room tiles and the vacancy table, while invoices use the plan. This is confusing and actively misleading today.
2. **Onboarding takes five unconnected steps** (approve, enrol, allocate, fee plan, advance/ID). Each step re-asks or ignores earlier information.
3. **Information typed that the system already knows:** plan name, default billing/due days, payment amount (the balance), received date (now), Aadhaar digits (entered twice), advance received (should default to the plan's configured advance), branch on every form (could default to the selected branch), temporary passwords (could be generated).
4. **Overloaded pages:** Overview (~70 rows), Fees (3 tables), Analytics (8 tables). Cards do not link to the filtered list they summarise.
5. **No bed concept.** Counts are right, but "which bed" cannot be shown. Fine for most hostels if beds are interchangeable; needed only if residents are assigned to a named bed.
6. **Per-row action overload** on Residents (six controls) and Fees (Receipt next to Reverse).
7. **Inconsistent filters:** now standardised on five screens, still missing on Branch admins, Stay requests, and the Fees ledger uses its own different controls.
8. **Wrong or misleading labels:** "Edit branch" dialog titled "Add a branch"; filter "Room" meaning allocation status; "Verified property photograph HTTPS URL"; "WhatsApp mobile" while codes are off.
9. **Free-text where a choice exists:** floor, plan name, facilities.
10. **No guided empty states or first-run checklist** (add branch → rooms → plans → publish), which a new owner needs.

## 4. Proposed simplifications (nothing removed; most are defaults and grouping)

| # | Change | Removes typing / steps | Risk |
|---|---|---|---|
| A | Single price source shown everywhere: show the active fee plan price on rooms; hide room fee when a plan exists | 1 field per room, removes ₹0 confusion | Low |
| B | Onboarding wizard from an approved admission (room → plan auto → advance pre-filled → password generated) | 5 steps become 1 flow | Medium, existing endpoints reused |
| C | Smart defaults: payment amount = balance; payment time = now; plan name from fields; billing day 1, due day 5 | about 6 fields | Low |
| D | Clickable KPI cards and one branch selector on Overview; move long tables to their pages | 1 long page → 4 short views | Low |
| E | Group resident row actions under one menu; auto-assign the plan on allocation | 2 steps | Low |
| F | Fix labels/titles (Edit branch, Room filter, WhatsApp mobile optional) | confusion | Very low |
| G | Room form: floor as number, unique per branch, plan price read-only | 1 field + naming hacks | Medium (migration for uniqueness) |
| H | Tabs for Fees and Analytics, summary cards on top | scrolling | Low |
| I | First-run checklist and guided empty states | onboarding | Low |
